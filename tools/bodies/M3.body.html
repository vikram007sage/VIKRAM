00 / ORIENTATION

The three building blocks

RAG

Retrieve relevant text from your documents, give it to the model, answer from it with citations. Solves: private and fresh knowledge, fewer hallucinations.

Agents

A model in a loop that decides which tool to call (search, database, API, code), observes the result, and continues until the task is done.

Evals

Test sets and metrics that tell you whether a change made the system better — the difference between a demo and a product.

Your CV gap → opportunity: the roadmap in VIKRAM has "Project 2: RAG app with an eval set" due 31 March 2027. Section 6 gives a brief for exactly that project, using your own notes as the corpus.
01 / RAG

The RAG pipeline, choice by choice

core
1. IngestParse PDFs, HTML, docs; clean headers/footers; keep metadata (title, section, date, source URL, access permissions).
2. ChunkSplit into 200–1,000-token pieces with 10–20% overlap; better: split on structure (headings, paragraphs, table rows). A 250k-token handbook at 500-token chunks with 50 overlap → ~556 chunks.
3. EmbedAn embedding model turns each chunk into a vector. Choose for language (multilingual if Hindi/Indic content), domain and cost.
4. IndexVector database or library (FAISS, Chroma, pgvector, Pinecone, Weaviate, Qdrant) with approximate nearest-neighbour search (HNSW).
5. RetrieveEmbed the question; top-k by cosine similarity. Better: hybrid search (vector + BM25 keyword search) to catch exact terms like product codes, plus metadata filters (date, user's permissions).
6. Re-rankA cross-encoder re-ranker scores (question, chunk) pairs more accurately; keep top 3–8.
7. GeneratePrompt: "Answer only from the context; cite chunk ids; say you don't know if the answer isn't there."
8. Evaluate + monitorRetrieval and answer metrics separately (section 4); log queries with no good results.
ProblemLikely causeFix

Variants to name: GraphRAG (build a knowledge graph of entities for "global" questions), agentic RAG (model decides when and what to retrieve), long-context models as an alternative for small corpora (simpler but costlier per query).
02 / AGENTS

Agents: patterns and protocols

2026
Tool callingYou describe tools (name, purpose, JSON schema of arguments); the model outputs a structured call; your code executes it and returns the result.
ReAct loopReason → act (call tool) → observe → repeat → final answer. Cap the number of steps.
Planner–executorOne step makes a plan; others execute sub-tasks; good for long tasks.
Workflows vs agentsFixed sequences of LLM calls (workflows) are more predictable; use open-ended agents only when steps can't be known in advance.
Multi-agentSpecialised agents (researcher, writer, checker) coordinating; adds cost and failure points — justify it.
MemoryShort-term (conversation), long-term (stored facts/preferences in a database), retrieved when relevant.
ProtocolWhat it standardises
Model Context Protocol (MCP)How an AI application connects to tools and data (servers expose tools/resources; clients like assistants or IDEs call them). Introduced by Anthropic in November 2024; adopted by OpenAI, Google and Microsoft; ~97 million monthly SDK downloads by March 2026 and thousands of public servers
Agent2Agent (A2A)How agents from different vendors delegate tasks to each other; started by Google, now under the Linux Foundation
AGENTS.md and similarInstructions files that tell coding agents how to work in a repository
Safety for agents: least-privilege tools, human approval for irreversible or money-moving actions, treat all tool output and web content as untrusted (prompt injection), log every action, sandbox code execution, step and spend limits.
03 / ECONOMICS

Cost and latency of agents

Example: an agent takes 6 steps; each call sends ~4,000 input tokens (growing context) and gets ~300 output tokens; at $3 / $15 per million → 6 × (0.012 + 0.0045) ≈ $0.10 per task (≈ ₹8). At 10,000 tasks a day that's ~$1,000/day. Levers: smaller model for routine steps, prompt caching of the fixed system prompt and tool definitions, trimming context, fewer steps via a better plan.

Rule of thumb: agents multiply cost and latency by the number of steps. Always compare against a simpler workflow on the same eval set.

Worked metrics

Retrieval: 5 test questions; the relevant chunk appears at ranks 1, 3, not found, 2, 1. Recall@3 = 4/5 = 0.80. MRR = (1 + 1/3 + 0 + 1/2 + 1) ÷ 5 ≈ 0.57.

Answers: 200 graded answers: 170 correct (85%), 18 hallucinated (9%), 12 correctly refused (6%). Target the 9% first: inspect whether retrieval failed (fix search) or generation ignored context (fix prompt/model).

Building the eval setStart with 50–200 real or realistic questions, include hard and "not answerable" ones, label expected answers and sources; grow it from production failures.
LLM-as-judgeFast and scalable; check it against human grades on a sample (agreement rate), use clear rubrics, watch for bias toward longer answers or its own outputs.
Regression testingRun the eval set on every prompt, model or retrieval change before shipping.
ToolsRagas, DeepEval, promptfoo, LangSmith, Arize Phoenix, OpenAI Evals — or a simple spreadsheet + script to start.
05 / PRODUCTION

Production concerns

Observability

Trace every request: prompt, retrieved chunks, tool calls, tokens, latency, cost, user feedback.

Guardrails

Input filters (PII, abuse), output checks (format validation, policy), structured outputs (JSON schemas), fallbacks to human.

Data + privacy

Don't send sensitive data without agreements; mask PII; India's DPDP Act consent rules; RBI expectations for regulated entities using AI.

Versioning

Version prompts, indexes and model choices; re-run evals when a provider updates a model.

Frameworks

LangChain/LangGraph, LlamaIndex, provider agent SDKs; or plain code — frameworks help speed, plain code helps debugging.

Caching

Cache embeddings, frequent answers and prompt prefixes.
