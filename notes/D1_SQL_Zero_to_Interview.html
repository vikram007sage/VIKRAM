01 / MENTAL MODEL

Written order vs execution order

core
Written: SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
Executed: FROM / JOIN → WHERE → GROUP BY → HAVING → SELECT (window functions here) → DISTINCT → ORDER BY → LIMIT

Why it matters

You can't use a SELECT alias in WHERE (WHERE runs first). You can't filter on a window function in WHERE either: wrap it in a subquery or CTE. HAVING filters groups, WHERE filters rows.

Grain

Before writing, say the grain of the output: "one row per customer per month". Most wrong answers come from joining tables at different grains and double-counting.

Talk while you type

"I'll join cards to txns on card_id, group by customer, and use LEFT JOIN so customers with no spend still appear." Interviewers give credit for reasoning even if a comma is off.

02 / BASICS

SELECT, WHERE, GROUP BY, HAVING

-- customers per city
SELECT city, COUNT(*) AS customers
FROM customers
GROUP BY city
ORDER BY customers DESC;

-- categories with more than ₹5 lakh spend
SELECT merchant_category,
       COUNT(*)              AS n,
       ROUND(SUM(amount), 0) AS spend,
       ROUND(AVG(amount), 0) AS avg_ticket
FROM txns
GROUP BY merchant_category
HAVING SUM(amount) > 500000
ORDER BY spend DESC;
COUNT(*)counts rows; COUNT(col) skips NULLs; COUNT(DISTINCT col) counts unique values.
FiltersIN (...), BETWEEN a AND b (inclusive), LIKE 'Mum%', IS NULL / IS NOT NULL (never = NULL).
Integer divisionIn many engines 7/2 = 3. Multiply by 100.0 or CAST to get a decimal percentage.
Every non-aggregated columnin SELECT must be in GROUP BY (MySQL lets you break this; don't).
03 / JOINS

Joins, and the two bugs they cause

most tested
JoinKeepsUse for
INNER JOINonly matching rows"customers with transactions"
LEFT JOINall of the left table; NULLs where no match"all customers, including those with zero spend"; finding missing records
FULL OUTER JOINeverything from bothreconciling two systems
CROSS JOINevery combinationbuilding a date × product grid
Self jointable joined to itselfduplicates, employee–manager, consecutive events
-- top 5 customers by spend (customer → cards → txns)
SELECT c.customer_id, c.name, ROUND(SUM(t.amount), 0) AS spend
FROM customers c
JOIN cards k ON k.customer_id = c.customer_id
JOIN txns  t ON t.card_id     = k.card_id
GROUP BY c.customer_id, c.name
ORDER BY spend DESC
LIMIT 5;

-- customers who never transacted (anti-join)
SELECT c.customer_id, c.name
FROM customers c
LEFT JOIN cards k ON k.customer_id = c.customer_id
LEFT JOIN txns  t ON t.card_id     = k.card_id
WHERE t.txn_id IS NULL
GROUP BY c.customer_id, c.name;

Bug 1: fan-out

Joining customers to cards (one-to-many) and then to payments and txns multiplies rows: each txn repeats for every payment. Aggregate each child table in its own CTE first, then join the summaries.

Bug 2: LEFT JOIN turned INNER

A WHERE condition on the right table (WHERE t.channel = 'UPI') removes the NULL rows. Put the condition in the ON clause instead: LEFT JOIN txns t ON ... AND t.channel = 'UPI'.

Duplicate keys

Always ask: is the join key unique on at least one side? If both sides have duplicates you get a many-to-many explosion.

04 / LOGIC

CASE WHEN, NULLs, subqueries and CTEs

-- late-or-missed payment rate and revolve rate in one pass
SELECT
  ROUND(100.0 * SUM(CASE WHEN paid_date IS NULL OR paid_date > due_date THEN 1 ELSE 0 END) / COUNT(*), 1) AS late_or_missed_pct,
  ROUND(100.0 * SUM(CASE WHEN amount_paid < amount_due THEN 1 ELSE 0 END) / COUNT(*), 1)                AS revolve_pct
FROM payments;

-- pivot: spend by channel × category
SELECT channel,
       SUM(CASE WHEN merchant_category = 'travel'  THEN amount END) AS travel,
       SUM(CASE WHEN merchant_category = 'grocery' THEN amount END) AS grocery,
       SUM(CASE WHEN merchant_category = 'dining'  THEN amount END) AS dining
FROM txns
GROUP BY channel;

-- customers earning above average (scalar subquery)
SELECT customer_id, name, income
FROM customers
WHERE income > (SELECT AVG(income) FROM customers);
NULL logicNULL = NULL is not true. NULL + 5 is NULL. AVG ignores NULLs (so the denominator shrinks). COALESCE(x, 0) replaces NULL.
CTEWITH name AS (SELECT ...) SELECT ... FROM name. Use one CTE per logical step; name them by what they hold (monthly_spend, first_txn).
EXISTS vs INNOT IN breaks if the subquery returns any NULL (returns nothing). Prefer NOT EXISTS or a LEFT JOIN anti-join.
UNION vs UNION ALLUNION removes duplicates (slower); UNION ALL keeps them. Default to UNION ALL unless you need distinct rows.
05 / WINDOWS

Window functions: the topic that separates candidates

must
function() OVER (PARTITION BY group ORDER BY sort ROWS BETWEEN ... AND ...)

A window function computes over a set of rows related to the current row without collapsing them (unlike GROUP BY).

FunctionTies 100, 90, 90, 80 →Use
ROW_NUMBER()1, 2, 3, 4pick exactly one row per group (latest, first, dedupe)
RANK()1, 2, 2, 4competition ranking with gaps
DENSE_RANK()1, 2, 2, 3"Nth highest" with ties counted once
LAG / LEAD(col, n)value n rows before / after: month-over-month change, time between events
SUM / AVG OVERrunning totals, moving averages, share of total
NTILE(n)split into quartiles / deciles
FIRST_VALUE / LAST_VALUEfirst or last value in the window (LAST_VALUE needs a full frame)
-- month-over-month spend growth
WITH m AS (
  SELECT strftime('%Y-%m', txn_date) AS month, SUM(amount) AS spend
  FROM txns GROUP BY month
)
SELECT month, ROUND(spend, 0) AS spend,
       ROUND(100.0 * (spend - LAG(spend) OVER (ORDER BY month))
             / LAG(spend) OVER (ORDER BY month), 1) AS mom_pct
FROM m ORDER BY month;

-- running total and 3-transaction moving average per card
SELECT card_id, txn_date, amount,
       SUM(amount) OVER (PARTITION BY card_id ORDER BY txn_date, txn_id
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       AVG(amount) OVER (PARTITION BY card_id ORDER BY txn_date
                         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)         AS moving_avg_3
FROM txns;
Frame default trap: with ORDER BY and no frame, most engines use RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which treats tied dates as one block. Write ROWS explicitly and add a tie-breaker (txn_id) to ORDER BY.
06 / PATTERNS

Nine patterns that answer most questions

core
1 · Top N per group (top 2 spenders in each city)
WITH s AS (
  SELECT c.city, c.customer_id, SUM(t.amount) AS spend
  FROM customers c JOIN cards k USING (customer_id) JOIN txns t USING (card_id)
  GROUP BY c.city, c.customer_id
)
SELECT city, customer_id, spend, rnk
FROM (SELECT *, DENSE_RANK() OVER (PARTITION BY city ORDER BY spend DESC) AS rnk FROM s)
WHERE rnk <= 2
ORDER BY city, rnk;
2 · Nth highest (second-largest transaction per card)
WITH ranked AS (
  SELECT card_id, amount, ROW_NUMBER() OVER (PARTITION BY card_id ORDER BY amount DESC) AS r
  FROM txns
)
SELECT card_id, amount AS second_highest FROM ranked WHERE r = 2;

Use DENSE_RANK if "second highest distinct value" is meant. Clarify which.

3 · First / latest record (first transaction of each card)
SELECT card_id, txn_date
FROM (SELECT card_id, txn_date,
             ROW_NUMBER() OVER (PARTITION BY card_id ORDER BY txn_date, txn_id) AS rn
      FROM txns)
WHERE rn = 1;
4 · Period-over-period change

LAG on a monthly aggregate (section 5). For year-over-year on monthly data, use LAG(spend, 12).

5 · Running total / share of total
SELECT merchant_category, SUM(amount) AS spend,
       ROUND(100.0 * SUM(amount) / SUM(SUM(amount)) OVER (), 1) AS share_pct
FROM txns GROUP BY merchant_category;

SUM(SUM(amount)) OVER () = a window over the grouped result: the grand total.

6 · Retention cohort (of customers who first spent in month M, how many spent in M+1?)
WITH first AS (
  SELECT k.customer_id, MIN(strftime('%Y-%m', t.txn_date)) AS cohort
  FROM cards k JOIN txns t USING (card_id) GROUP BY k.customer_id
), act AS (
  SELECT DISTINCT k.customer_id, strftime('%Y-%m', t.txn_date) AS month
  FROM cards k JOIN txns t USING (card_id)
)
SELECT f.cohort,
       COUNT(DISTINCT f.customer_id) AS size,
       COUNT(DISTINCT CASE WHEN a.month = strftime('%Y-%m', date(f.cohort || '-01', '+1 month'))
                           THEN a.customer_id END) AS active_next_month
FROM first f LEFT JOIN act a USING (customer_id)
GROUP BY f.cohort ORDER BY f.cohort;
7 · Gaps and islands (longest streak of consecutive spending days)
WITH d AS (SELECT DISTINCT card_id, date(txn_date) AS d FROM txns),
g AS (
  SELECT card_id, d,
         julianday(d) - ROW_NUMBER() OVER (PARTITION BY card_id ORDER BY d) AS grp
  FROM d
)
SELECT card_id, MIN(d) AS start, MAX(d) AS finish, COUNT(*) AS days
FROM g GROUP BY card_id, grp
HAVING COUNT(*) >= 2
ORDER BY days DESC;

The trick: date minus row number is constant within a run of consecutive days.

8 · Duplicates (same card, amount and date twice: possible double charge)
SELECT a.card_id, a.txn_id AS t1, b.txn_id AS t2, a.amount, a.txn_date
FROM txns a
JOIN txns b ON a.card_id = b.card_id AND a.amount = b.amount
           AND a.txn_date = b.txn_date AND a.txn_id < b.txn_id;

To delete duplicates, keep ROW_NUMBER() = 1 per key.

9 · Ratio / conditional aggregation (UPI share of spend by city)
SELECT c.city,
       ROUND(100.0 * SUM(CASE WHEN t.channel = 'UPI' THEN t.amount ELSE 0 END) / SUM(t.amount), 1) AS upi_share_pct
FROM customers c JOIN cards k USING (customer_id) JOIN txns t USING (card_id)
GROUP BY c.city ORDER BY upi_share_pct DESC;

08 / BEYOND CORRECT

Performance, indexes and checking your own answer

Indexes

An index is a sorted lookup on a column (like a book index). It speeds WHERE, JOIN and ORDER BY on that column but slows inserts. Functions on an indexed column (WHERE YEAR(d) = 2026) stop the index being used; write a range instead (d >= '2026-01-01' AND d < '2027-01-01').

Big-data engines

BigQuery and Snowflake charge or slow down by data scanned. Select only needed columns (never SELECT * on a big table), filter on the partition column (usually a date), and aggregate before joining.

Sanity checks

Count rows before and after each join. Check for NULLs in join keys. Compare a total to a known figure. Look at 5 sample rows. Say these checks out loud in an interview.

NormalisationSplit data so each fact lives once (customers vs cards vs txns). Analytics warehouses often denormalise into a wide fact table plus dimension tables (star schema).
Primary / foreign keycard_id is the primary key of cards and a foreign key in txns.
OLTP vs OLAPTransaction systems (fast writes, row stores like MySQL/Postgres) vs analytics warehouses (big scans, column stores like BigQuery, Snowflake, Redshift).
Using AILLMs write decent first drafts of SQL, so interviews now probe whether you can spot when a query is wrong: fan-out, NULL handling, wrong grain. Learn to read SQL critically, not just write it.

-- Q7 share of spend from top 10% of customers
WITH s AS (SELECT k.customer_id, SUM(t.amount) AS spend
           FROM cards k JOIN txns t USING (card_id) GROUP BY k.customer_id),
d AS (SELECT *, NTILE(10) OVER (ORDER BY spend DESC) AS decile FROM s)
SELECT ROUND(100.0 * SUM(CASE WHEN decile = 1 THEN spend END) / SUM(spend), 1) FROM d;

-- Q11 late in two consecutive months
WITH l AS (SELECT card_id, due_date,
                  CASE WHEN paid_date IS NULL OR paid_date > due_date THEN 1 ELSE 0 END AS late
           FROM payments),
x AS (SELECT *, LAG(late) OVER (PARTITION BY card_id ORDER BY due_date) AS prev_late FROM l)
SELECT DISTINCT card_id FROM x WHERE late = 1 AND prev_late = 1;

-- Q18 spend fell 50%+ from Q1 to Q2 2026
WITH q AS (SELECT k.customer_id,
             SUM(CASE WHEN t.txn_date < '2026-04-01' THEN amount ELSE 0 END) AS q1,
             SUM(CASE WHEN t.txn_date >= '2026-04-01' THEN amount ELSE 0 END) AS q2
           FROM cards k JOIN txns t USING (card_id) GROUP BY k.customer_id)
SELECT customer_id, q1, q2 FROM q WHERE q1 > 0 AND q2 <= 0.5 * q1;

-- Q21 median without a MEDIAN function
WITH o AS (SELECT amount, ROW_NUMBER() OVER (ORDER BY amount) AS rn, COUNT(*) OVER () AS n FROM txns)
SELECT AVG(amount) FROM o WHERE rn IN ((n + 1) / 2, (n + 2) / 2);

-- Q25 new vs returning spenders per month
WITH m AS (SELECT DISTINCT k.customer_id, strftime('%Y-%m', t.txn_date) AS month
           FROM cards k JOIN txns t USING (card_id)),
f AS (SELECT customer_id, MIN(month) AS first_month FROM m GROUP BY customer_id)
SELECT m.month,
       SUM(CASE WHEN m.month = f.first_month THEN 1 ELSE 0 END) AS new_spenders,
       SUM(CASE WHEN m.month > f.first_month THEN 1 ELSE 0 END) AS returning_spenders
FROM m JOIN f USING (customer_id) GROUP BY m.month ORDER BY m.month;
