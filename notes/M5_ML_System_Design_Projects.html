01 / TEMPLATE

The nine-step template

core
1. Business goal + constraintsWhat decision does the model drive? Latency (real-time vs batch), scale, regulation, explainability needs.
2. ML framingClassification, regression, ranking, forecasting, clustering? What exactly is the label and when is it known?
3. DataSources, volume, label quality, class balance, how to split (time-based for anything with time).
4. FeaturesRaw → engineered (aggregates over windows, ratios, recency/frequency), available at prediction time (no leakage), stored in a feature store for consistency.
5. BaselineRules or logistic regression first; then gradient-boosted trees (XGBoost/LightGBM) — the default for tabular data; deep learning for text, images, sequences.
6. Offline evaluationMetric matching the cost of errors: precision/recall at a threshold, PR-AUC for imbalance, ROC-AUC/Gini/KS for credit, NDCG for ranking, MAPE for forecasts; calibration if probabilities are used.
7. DeploymentBatch scoring vs real-time API; latency budget; shadow mode before switching on; fallback rules.
8. Online evaluationA/B or champion–challenger test on the business metric (P2, D3).
9. Monitoring + iterationData drift (PSI), prediction drift, performance once labels arrive, retraining schedule, feedback loops, fairness checks.
Say early: "Before choosing a model, I'd confirm the label, when it becomes available, and how much each kind of error costs." This one sentence separates strong candidates.
02 / PRACTICE

Three worked designs

try first
1 · Real-time card fraud detection

Goal: block fraudulent transactions with <100 ms added latency while keeping false declines low (each false decline annoys a good customer). Label: chargeback or customer-reported fraud — arrives days to weeks later; fraud rate often well under 1%. Features: amount vs customer's usual, merchant category, new device or location, transactions in last 1/10/60 minutes (velocity), distance from last transaction, card-not-present flag, merchant risk score. Model: rules + gradient-boosted trees; graph features for fraud rings. Metric: recall at a fixed false-positive rate, or expected loss saved minus cost of declines. Deploy: real-time scoring; three actions — approve, step-up authentication (OTP), decline. Monitor: fraudsters adapt (concept drift) → frequent retraining; delayed labels → use proxy labels.

2 · Credit scoring for a first-time card applicant ("new to credit")

Goal: approve good borrowers without bureau history. Label: 90+ days past due within 12 months of issue (needs a long window; use vintage data). Features: bank-statement cash flows (with consent via the Account Aggregator framework), income stability, UPI transaction patterns, employer, device data within rules. Model: logistic regression scorecard (explainable, regulator-friendly) vs gradient boosting with SHAP explanations. Metric: Gini/KS, approval rate at a target loss rate, calibration. Issues: reject inference (you only see outcomes for approved applicants), fairness, RBI expectations on explainability and digital lending rules. Monitor: PSI on features, vintage curves.

3 · Search ranking for a quick-commerce app

Goal: users find and add items fast. Label: add-to-cart after a search (implicit feedback). Pipeline: retrieval (keyword + embeddings, handle Hinglish and misspellings like "atta"/"aata") → ranking model (learning-to-rank with gradient-boosted trees: relevance, popularity in this dark store, in-stock, price, personal history) → business rules (out-of-stock removed). Metric: NDCG offline; online search-to-cart conversion, zero-result rate. Pitfalls: position bias in clicks, cold start for new items.

03 / PRODUCTION

Production topics interviewers probe

TopicWhat to say
Data leakageFeatures that wouldn't exist at prediction time (e.g. "days to chargeback"); split by time; build features as of the prediction timestamp
Class imbalanceUse PR-AUC, class weights, threshold tuning; resampling only on training data
Train–serve skewSame feature code for training and serving; feature store
DriftPSI > 0.25 on a key feature = investigate; monitor score distribution and approval rates
Feedback loopsThe model's decisions change future data (declined users never show repayment); keep a small random exploration/holdout group
ExplainabilitySHAP values, reason codes for declines (regulated lending)
FairnessCheck outcomes across groups; avoid proxies for protected attributes
MLOpsVersioned data and models (MLflow), CI for models, automated retraining, rollback
LLMs in the stackUse LLMs for text features (complaint classification, document extraction) or as a component; keep classical ML for structured risk decisions (M3)
04 / YOUR PROJECTS

Your two ML projects as interview stories

personal
LIG sensor fabrication optimiser (Gaussian Process + batch Bayesian optimisation)

60-second version: "Making good laser-induced graphene depends on several laser and substrate parameters, and each experiment costs time and material. I built a Gaussian Process surrogate model that predicts sheet resistance from fabrication parameters and gives uncertainty. Using Bayesian optimisation with Kriging Believer batching, it proposes several experiments at once, choosing points that are either promising or uncertain. It cut the search for optimal parameters from about 500 trials to around 60. I deployed it on Streamlit with Supabase so lab members can log results, and added transfer learning between similar carbon materials."

Expect these follow-ups: Why a GP and not a neural net? (Small data, uncertainty estimates, smooth response.) Which kernel? (Matérn is a common default; say what you used.) Which acquisition function? (Expected improvement / UCB — know yours.) What is Kriging Believer? (Pretend the model's prediction at a chosen point is the true result, update, pick the next point — gives a batch.) How did you validate "500 → 60"? (Be precise: compared against what baseline? Raman-validated runs?) Limits? (GPs scale poorly beyond a few thousand points; high dimensions.)

Tourist arrival prediction (SARIMA vs LSTM)

60-second version: "I forecast weekly regional tourist arrivals using 11 years of arrival and search data. A SARIMA model with a rolling forecast captured the strong yearly seasonality and beat LSTM models; I extracted three seasonal patterns useful for planning."

Fix before interviews (from S4): your CV says "0.989 R" — say whether it is correlation R or R², and add an error metric interviewers trust for forecasts (MAPE or RMSE on a hold-out period). Follow-ups: How did you choose (p,d,q)(P,D,Q,s)? (ACF/PACF, AIC.) Stationarity test? (ADF.) Why did SARIMA beat LSTM? (Small data, clear seasonality; LSTMs need more data.) How was the rolling forecast done? (Re-fit/forecast one step ahead, no peeking.) What would you add? (Holiday effects, Prophet or gradient boosting with lag features, prediction intervals.)

Also usable: CheQ A/B tests (experimentation, P2) and your planned RAG project (M3). Interviewers value an honest "what went wrong" — prepare one mistake per project.
